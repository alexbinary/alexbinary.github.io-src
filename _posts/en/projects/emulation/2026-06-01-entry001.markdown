I play video games on emulators and I understand the basic principles of emulation, but I want to learn more and get my hands dirty. I'd like to know how to write a Game Boy emulator, and it's probably doable with enough patience, but I like to start with the basics. And the basics are: "What exactly is emulation?"

To answer that I set out to build a simple, programmable hardware system and write an emulator for it. I chose to use the 6502 processor and its 6522 interface, taking inspiration from [Ben Eater's excellent video series where he builds a minimal computer based on the 6502](https://www.youtube.com/playlist?list=PLowKtXNTBypFbtuVMUVXNR0z1mu7dp7eH). User input and output will be minimal at first, using just simple buttons and LEDs, and maybe a small OLED screen.

This project is mainly an exploration. It is a way for me get hands on experience with low level hardware concepts and hardware/software interactions. With this kind of discovery projects, I like to start form first principles and work my way up. I experiment step by step and check whether what I think I know is actually true, to build a strong understanding.


## Understanding emulation

Let's take the Game Boy as an example. A Game Boy game is a program designed to be read by the Game Boy's hardware in order to produce images and sound based on the user's button presses. The goal of a "Game Boy emulator" is then to take this program as input and recreate the gaming experience on a PC, that is, to generate the same images and sounds based on the user's actions, but on a completely different hardware stack.

To write an emulator one needs to understand how each instruction in the program affect the images and sounds that are generated by the hardware. Writing an emulator therefore requires a good understanding of the original hardware and its interaction with the software, but the goal is not necessarily to faithfully reproduce the internal workings of the hardware. What matters is the *observable* result.


## Hardware used on this project

I chose to build a system based on the [6502](https://www.westerndesigncenter.com/wdc/documentation/w65c02s.pdf) microprocessor. The 6502 is a relatively simple microprocessor, ideal for beginners. It's also very well-known, being the CPU of many consumer devices in the 1980s, notably the Apple II, Commodore 64 and Atari 2600. Modernized versions are still in production today, and there's a large community of enthusiasts.

Besides the 6502, I choose an [AT28C256](https://ww1.microchip.com/downloads/en/DeviceDoc/doc0006.pdf) EEPROM to store the program, a [62256](https://eater.net/datasheets/hm62256b.pdf) RAM to give the CPU some working memory, and 74LSXX logic gates for address decoding. LEDs and buttons will be connected to the 6502 through the [6522](https://eater.net/datasheets/w65c22.pdf) interface adapter. An SSD1306 OLED screen will connect through an i2c bus. I am working on breadboards and use my [Arduino Uno R4 Wi-Fi](https://docs.arduino.cc/resources/datasheets/ABX00087-datasheet.pdf) to program the EEPROM, monitor signals, and experiment with components, and as a power adapter.


## First steps with the 6502

Being a microprocessor, the 6502's main function is to execute instructions. Unlike a microcontroller, it has no internal memory or peripherals. It interacts with the outside world via a data and address bus, on which it can read and write data. The instructions to be executed, the data to be processed, and the output data all pass through the bus. Generally, a memory containing the program and working data is connected to the bus, along with peripherals such as a display, a sound card, etc.

To get started, I'm following [Ben Eater's video series dedicated to building a computer based on the 6502](https://www.youtube.com/playlist?list=PLowKtXNTBypFbtuVMUVXNR0z1mu7dp7eH). I begin by mounting the 6502 on a breadboard, connecting the power supply and basic control signals, and adding a reset button. The clock signal is generated by a module based on a 555 timer circuit that I built previously following [Ben Eater's videos on the subject](https://www.youtube.com/watch?v=kRlSFm519Bo). I'm using my Arduino Uno R4 Wi-Fi as a power source and for making observations afterward.

To verify that something is happening in the processor, I connect the four least significant bits of the address bus to four LEDs, and they indeed show activity. I also connected the data bus lines directly to the power supply or ground using resistors so that every time the CPU reads data from the bus, it retrieves the value `0xEA`, which corresponds to the `NOP` ("No Operation") instruction. When observing the address lines, we see a count, which corresponds to the CPU reading instructions one after another from memory.

I then connected the address lines to the Arduino along with the clock signal and wrote a simple program to read and display the data at each clock tick via an interrupt. Ben Eater uses an Arduino Mega to observe all 16 address lines and 8 data lines, but my Arduino Uno doesn't have enough pins to allow me to observe all the lines, so I focused on just the 4 least significant bits of the address.

When the processor starts or is reset, it looks for the address of the first instruction to execute. To do this, it reads a 16 bit address from addresses `0xFFFC` and `0xFFFD`, then starts fetching instructions from that address. Since I'm only observing the last 4 bits of the address, I expect to see the values ​​`C` and `D`, which correspond to the binary values `​​1100` and `1101` respectively. When I press the reset button, I do indeed see these addresses. Since the data bus is wired to return `0xEA`, the CPU will start reading instructions from address `0xEAEA`. The binary value `A` is `1010`, and it's indeed the first address we see after `C` and `D`. Very cool!
