## Introduction

In the current state of my [optics simulation software](/en/projects/optics-simulator), object placement is constrained to a single optical axis. I want to evolve the software to allow objects to be positioned more freely in a two-dimensional space.

I want to create a workspace where users can use the mouse to position and orient objects freely in two dimensions. I want the workspace to be virtually infinite and independent of the window size, allowing users to pan, zoom, and rotate freely, as seen in similar software.

Since this approach is fundamentally different from the current version, I decided to start from scratch. The basic concept was implemented quickly thanks to the features provided by SwiftUI and the Canvas API, but the more advanced functionality required me to dive into the mathematical details of affine transformations. The hardest part turned out to be formulating each problem correctly; once that was done, the calculations themselves were relatively straightforward.

A rigorous mathematical analysis of the different problems allowed me to derive equations that I was then able to implement successfully in code. A second round of analysis revealed that the three problems I had studied shared a common foundation, and I reorganized the code accordingly.

In this post, I describe the complete process.


## Implementing basic functionality

In SwiftUI, the origin of the `Canvas` is located in the top-left corner, with X values increasing to the right and Y values increasing downward. Mouse events, however, are reported with their origin in the bottom-left corner, with Y values increasing upward.

I therefore apply an initial set of transformations to align the coordinate systems before drawing on the canvas. First, I scale the Y axis by a factor of `-1` to flip the coordinate system upward, then I translate it downward by the height of the window to move the origin to the bottom-left corner.

At this point, the view coordinates coincide with the canvas coordinates. In other words, if an object is drawn at coordinates (100, 200) in the `Canvas`, it will appear at screen coordinates (100, 200). In particular, this makes it possible to use the mouse coordinates directly to draw a point that appears to follow the cursor.

To implement the infinite workspace, I successively apply a translation, a rotation, and a scaling transformation, and use mouse and trackpad events such as scrolling, pinching, and rotation gestures to update their values. To keep the mouse coordinates aligned with the workspace, each transformation must be compensated for. The corresponding code is fairly straightforward to derive.

At this point, we have a workspace in which the user can move around freely. However, zooming and rotation are still performed relative to the origin of the coordinate system, which is not particularly ergonomic. I want both operations to be centered around the mouse cursor instead. I also want to implement a feature that centers the view on a given region while adjusting the zoom level if necessary.

After a few experiments, these tasks turned out to be more challenging than I had expected.


## Looking for a proper model

I decided to focus on zooming first. At first, I wasn't quite sure how to approach the problem, so I started sketching it out on paper. I quickly realized that the goal was to add a translation after the scaling operation to compensate for the movement of the point that was supposed to remain fixed at the center. I obtained an initial result, but the implementation did not behave correctly. I suspected that the existing translation applied before the scaling was making the problem more complicated. After a fair amount of trial and error, I still couldn't find a working solution.

## Analysis of the Results and Simplifications

The three equations I derived are very similar, although not completely identical. However, I suspected there was a common underlying principle.

In fact, all three problems boil down to finding the translation that must be applied so that a given point in world space ends up at a given point on the screen, while taking rotation and scaling into account.

For zooming and rotation around an arbitrary point, the goal is to compute the translation to apply after the transformation so that the point that was under the mouse cursor before the transformation remains at the same screen position afterward.

For viewport recentering, the center of the bounding box must end up at the center of the screen, while the final rotation and scale factor are determined from the bounding box and the window size.
